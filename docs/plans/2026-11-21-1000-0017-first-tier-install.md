## Goal in one sentence

The macOS package declares macOS 26 and the docs say Windows 11+ / macOS 26+ / Linux second-tier; both install guides (English, Chinese) describe what a learner on macOS 26 or 27 actually sees; a public Homebrew tap cask installs the published `.dmg`, clears its quarantine flag, quits the app on uninstall and zaps the data directory; and publishing a release updates that cask's version and SHA-256 with no manual step — proven by a dry run against the published v0.15.0 and a macOS CI job that installs from the tap.

## Risks (each with how it is detected)

- **`postflight_steps`/tap trust need a current Homebrew** → the install job prints `brew --version` and installs fully qualified; the guide names a current Homebrew; an old brew fails to load the cask and the job says so.
- **`xattr -rd` exits non-zero when a path lacks the attribute** → the job's reinstall/repeat run names the exact exit status; the fix follows that evidence (no pre-emptive weakening).
- **App Management/TCC blocks moving the app on the runner** → Homebrew's prompt note appears in the job log; the job fails loudly rather than skipping.
- **`brew audit --online` mismatch on the historical artifact** → v0.15.0's plist says 13.0 while the cask says 26; CI runs `--strict`, the record quotes the expected online message, and the first release built after P1 clears it.
- **The tap drifts from the template** → the install job compares the tap file's hash with the render, and the gate's golden render fails on a template edit.
- **Apple changes the flow** → the guide names its source and date; the owner's review covers the wording.
- **The deploy key leaks** → `secrets` scans the tree, the tool never prints the key and deletes the temp file, and the log shows only the ssh remote and the commit id.

## Amendments

One line per amendment, made where the step's row met the current Homebrew (HEAD `e40c695`, 2026-11-21) or the tree.

1. **P3 placeholder form.** The template carries `@VERSION@`/`@SHA256@`, not `{{VERSION}}`/`{{SHA256}}`: Homebrew's install-step runner expands its own `{{...}}` tokens at install time and leaves an unknown `{{...}}` verbatim (Cask-Cookbook, "Interpolation in steps blocks"), so the required `{{appdir}}` in `postflight_steps` would collide with a `{{...}}` leftover check. The check now matches any `@UPPERCASE_NAME@` token and deliberately not `{{...}}`; the self-test proves `{{appdir}}` survives the render while a leftover `@VERS1ON@` fails the gate.
2. **P3 `must_succeed:`.** The `xattr -rd` step runs with `must_succeed: false`, from the Cookbook's own rule for `run`: failure aborts the install, and a non-zero exit is expected for a cleanup command whose target state — no `com.apple.quarantine` on the app — is the state the step wants (`xattr -rd` exits non-zero when the path carries no such attribute, which a re-install over the cask produces). The template comment states the reason.
3. **Fact 1's rationale corrected.** `minos` is not unenforced: dyld refuses a binary whose Mach-O `minos` is newer than the running system. The effective floor is the higher of `LSMinimumSystemVersion` and `minos`; the plist key (26.0) is above the Go 1.27 linker's 13.0, so the key binds, not the Mach-O. Default 1's decision (no `-ldflags -macos`) stands unchanged.
4. **Default 1's rationale corrected** the same way: it keeps the Mach-O `minos` at 13.0 because the plist key is the binding and higher floor, not because macOS ignores `minos`.
5. **Carried from P2's reviews — Touch ID.** "or Touch ID" / "或触控 ID" removed from both guides (the step and its screenshot caption), the Chinese equivalents, and the release notes line: neither cited Apple page mentions it (102445 says click **Open**; mh40616, macOS 27 selected, says `Enter your login password, then click OK.`), and goal 0017's own wording is "enter their password".
