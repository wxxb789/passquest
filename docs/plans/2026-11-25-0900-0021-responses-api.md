## Goal in one sentence

A learner whose endpoint path ends in `/responses` gets the provider check, the tutor and the durable
brief exactly as a chat-completions learner does — **the endpoint path selects the wire format, with
no separate setting**, and the chat-completions path stays byte-identical — while the four direct
`@earendil-works` packages move together to the newest release the corporate npm feed serves, at least
1.6.0, with Done-when 5 reported **blocked by the feed** for as long as the feed's newest is 1.5.2.
Ordering (coordinator decision, 2026-11-25): the Responses work (P1–P3) is done on the pinned 1.5.2
and must not depend on 1.6.0; the package bump is its own **last** step (P5), and its disclosed
default while the feed serves 1.5.2 is *item 5 blocked*.

### 5. The official API reference: the six differences the goal names, plus `store` and error bodies

Fetched 2026-11-25 with `curl -sS -L` (artifacts `Q:/scratch/omp/g21/P0/responses-create.md`,
`chat-create.md`); the pages serve their markdown at
`https://developers.openai.com/api/reference/resources/responses/methods/create/index.md` (the
`platform.openai.com/docs/api-reference/responses/create` URL redirects there).

| What the app relies on | Chat completions | Responses (doc line in `responses-create.md`) |
|---|---|---|
| token limit field | `max_tokens` | `max_output_tokens` — "an upper bound for the number of tokens that can be generated … including … reasoning tokens", `minimum: 16` (:4954-4958) |
| temperature | `temperature`, 0..2 | same name, same range, `default: 1` (:5489) — no code difference; a reasoning model that rejects a non-default temperature rejects it on both formats (disclosure, not a mapping) |
| system/instruction text | a `messages[]` entry with `role: "system"` | `instructions` — "A system (or developer) message inserted into the model's context" (:4946-4950); the app's own choice for the tutor (Q-0021-02); pi-ai puts it in `input` (fact 4) |
| user text | `messages[]` `role: "user"`, `content` string | `input` — a string, or items; a user message carries `content: [{type:"input_text", text}]` (`:131-160`, the part at `:175-187`) |
| response text | `choices[0].message.content` | `output[]` items of type `message` whose `content[]` parts are `output_text` (`:11986-12000`, example `:17485-17500`); the doc's own advice is not to assume `output[0]` is the message |
| usage counts | `usage.prompt_tokens/completion_tokens` | `usage.input_tokens/output_tokens/total_tokens` (example `:17522-17532`) |
| incomplete/failed | `finish_reason: "length"` | `status` + `incomplete_details.reason` (`"max_output_tokens" \| "max_messages" \| "content_filter" \| "steered"`, `:6892-6900`), and a 200 response can carry `error` (`:6792`) |
| error bodies (HTTP 4xx/5xx) | `{"error":{"message":…,"type":…,"code":…}}` | same `error` object shape, so the tutor host's `providerMessage`/status classes need no branch (fact 3) |
| server-side storage | no such field | `store`, `default: true` — "If set to true, response data will be stored for at least 30 days" (:5461-5466) — the tutor sends `store: false` (Q-0021-02), which is also what pi-ai does on the durable path (fact 4, `openai-responses.js:266`) |

## Risks (each with how it is detected)

- **A fake accepts a body the real API would refuse** → every fake validates the request's key set and
  values (not just "a POST arrived"), so a wrong mapping fails the gate that owns the format; the gap
  that remains is a *gateway* that rejects fields the reference allows (`store`, `instructions`) —
  detected only by the owner's probe (Q-0021-08), recorded as an untested limit, never as coverage.
- **The chat-completions path moves while Responses is added** → the invariants (`sameBody`,
  `Body == json.Marshal`), the existing per-gate path/body assertions, and P1's before-capture vs
  P2/P3's after-capture; a difference is a failure to explain in the round's answer, not a golden
  update.
- **The host's derivation disagrees with Go's** → the tutor host re-derives and validates the posted
  bytes against its own mapping, so the disagreement is a `config_error` before any POST; the
  `provider-smoke`/`tutor-smoke` cases pin both directions (a responses endpoint with a chat body and
  a chat endpoint with a responses body).
- **The shape-agreement rule refuses a learner's existing registry** → impossible for an entry with
  an endpoint while the endpoint rule exists (a `/responses` endpoint could not be stored before this
  goal, fact 2); entries **without** an endpoint (the built-in custom row) are exempt by Q-0021-04,
  and `TestEmbeddedRegistryIsValidAndCoversRequiredProviders` (`registry_test.go:21`) is the
  detector if the exemption is forgotten; the registry tests show both mismatch refusals and both
  agreements.
- **A refine reader or the window's "exact request" panel reads a nil `Chat`** → the Go type change
  makes every reader a compile error, P2's list names all three, and the `note propose --refine`
  case over `/responses` in `tutor-smoke` is the end-to-end detector; `desktop-smoke/anki.ts` keeps
  the window's refine on the chat path.
- **The settings line trips the ux language audit** → `zh-ascii-words`
  (`harness/lib/ux-page.ts:697-699`) fires on a bare `chat`/`completions`/`responses` inside a
  Chinese line; Q-0021-06 wraps both suffixes in `<code translate="no">`, and this step's own
  `desktop-ux` run (the `settings-row` state) is the detector.
- **The transitional P1 tree accepts an endpoint no host speaks** → disclosed in P1 and closed in
  P2/P3; no gate asserts a `/responses` endpoint before P2, and the durable pass of P3 fails loudly
  at `durable-host.mjs:214-215` if that edit is forgotten.
- **The page line moves a shot nobody declared** → the step's bench run names every differing state;
  an undeclared difference is a red run, and a stale entry in the next run is red too (the P3 row
  removes P2's entry).
- **The durable stub's event sequence is wrong but the library tolerates it** → the library throws on
  a missing terminal event and on an unfinished tool call (`openai-responses-shared.js:683-705`), and
  the must-fail self-test case proves a neutralised responses branch fails the gate; the recorded
  bodies show the stub's answers were consumed.
- **1.6.0 never reaches the feed** → item 5 stays blocked by the goal's own rule; the record carries
  the listing and the 404, and the check is one command away from re-running. No fake bump, no manual
  registry override.
- **The feed serves the four direct pins but not a transitive** (`pi-codemode`, `pi-telemetry`) → the
  bump stops there: P5's check reads all six (`bun.lock:65-75`), `bun install` resolves the lock as

  Done-when 5's blocked reason in the same dated note.
- **The bump changes the durable host's requests** (the system-role bullet, or another change) → the
  before/after capture of the same scenario names every field that moved; if a change would break a
  non-OpenAI compatible provider, the record says so and the owner decides whether to keep the bump

  and `package-smoke` are advisory locally; the CI matrix decides, and the record names which rows
