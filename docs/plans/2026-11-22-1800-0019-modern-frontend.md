# 0019 — A modern frontend written for the engines Pass Quest supports: increment plan

Contract: [`../goals/0019-modern-frontend.md`](../goals/0019-modern-frontend.md).
Conventions: [`../conventions.md`](../conventions.md). Harness: [`../harness.md`](../harness.md).
Cross-platform rules: [`../cross-platform.md`](../cross-platform.md).
Base: `goal/0019-modern-frontend` at `63ce6e4`.

## Goal in one sentence

Write the desktop frontend against the engines Pass Quest actually ships on — current WebView2 on
Windows 11 and WKWebView on macOS 26 — by removing the old-engine workarounds or listing each with a
reason, replacing hand-built interactions with native platform features where that is simpler or
faster, and proving with before/after runs on Windows and macOS that launch time, the four main
interactions, the translucent layers' rendering cost and the bundle size are no worse beyond the
measured noise while nothing the learner sees changes unintentionally.

     (`actions/runner-images images/windows/Windows2025-Readme.md`, fetched 2026-11-22). The
     WebView2 **Evergreen** runtime "automatically updates to the latest version available"
     (`learn.microsoft.com/…/webview2/concepts/versioning`, section *Matching the Runtime version
     with the SDK version*), so a Windows 11 learner's runtime and the runner's are the same
     Chromium-major channel: the plan may assume **current stable Chromium** (157 at scout time) and
     every bench sample records the engine's own `navigator.userAgent`, so a number is never quoted
     without the engine build that produced it.
   - **macOS** (`macos-26`, the 0017 floor): image `20260824.0517.1` is macOS 26.6.1 with
     **Safari 26.6 (21624.4.5.11.5)** (`images/macos/macos-26-Readme.md`). WKWebView is the OS's
     WebKit framework (`developer.apple.com/documentation/webkit/wkwebview`); Safari 26.6 on the
     same OS is that framework's browser, so the WKWebView baseline is the **Safari 26.x WebKit**.
     macOS 27 ships a later WebKit; it is above the floor, not the baseline.
   - **Linux** (`ubuntu-latest`, second-tier): the label moves to Ubuntu 26.04 in November 2026
     (`actions/runner-images` issue 14748, the banner in both Ubuntu readmes). The gate installs
     `libwebkit2gtk-4.1-0` (`.github/workflows/gate.yml:61-65`), and Ubuntu's security pocket ships
     webkit2gtk **2.52.6** for both images — `2.52.6-0ubuntu0.24.04.1` (noble) and
     `2.52.6-0ubuntu0.26.04.1` (resolute) at `packages.ubuntu.com/{noble,resolute}/libwebkit2gtk-4.1-0`,
     fetched 2026-11-22 — so the runner's engine is 2.52.6 either way. MyGo does not link it: it
     `dlopen`s `libwebkit2gtk-4.1.so.0` (falling back to 4.0) when a window first shows a page
     (`mygo@v0.10.0/internal/linux/ffi.go:904-912`), and Pass Quest ships an AppImage, so the CI
     Linux run exercises the runner's 2.52.6, not a pinned copy. Linux stays second-tier: it must
     render and work, and no feature is adopted that 2.52.6 cannot run.
   - **JavaScript level: ES2024.** Chromium 157 and Safari 26.6 are far above it; WebKitGTK 2.52 is
     the oldest engine build in the matrix (2.52.0 released 2026-03-18,
     `webkitgtk.org/2026/03/18/webkitgtk2.52.0-released.html`) and its trunk generation is later
     than Safari 18.0, where WebKit already shipped ES2024's `v`-flag regex support
     (`webkit.org/blog/15865/webkit-features-in-safari-18-0/`, section *JavaScript*). `bun build`
     has no browser-version target (`--target` is `browser|bun|node`; `bun build --help`, Bun
     1.4.5), so the tsconfig `target`/`lib` is the only switch and nothing downlevels the output;
     the three engines' gate runs are the runtime proof.
   - **CSS features all three support** (WebKit landing release each; WebKitGTK 2.52 is a later
     trunk generation, Chromium shipped each long before 157):
     `<dialog>` and `:has()` and `@layer` — Safari 15.4
     (`webkit.org/blog/12445/new-webkit-features-in-safari-15-4/`); `inert` — Safari 15.5
     (`webkit.org/blog/12669/new-webkit-features-in-safari-15-5/`); container queries — Safari 16.0
     (`webkit.org/blog/13152/webkit-features-in-safari-16-0/`); `color-mix()` — Safari 16.2
     (`webkit.org/blog/13591/webkit-features-in-safari-16-2/`); CSS nesting — Safari 16.5
     (`webkit.org/blog/14154/webkit-features-in-safari-16-5/`, section *CSS Nesting*); the Popover
     API — Safari 17.0 (`webkit.org/blog/14445/webkit-features-in-safari-17-0/`);
     `transition-behavior` — Safari 17.4 (`webkit.org/blog/15063/webkit-features-in-safari-17-4/`,
     confirmed by the 18.0 post, section *Animating display*); `@starting-style` — Safari 17.5
     (`webkit.org/blog/15383/webkit-features-in-safari-17-5/`, section *Starting style*); today's

4. **What can be measured, and how.** The smoke hook evaluates one script in the page after load,
   bounded at 40 s + 10 s load grace under a 60 s process kill, and writes `{ok,value}` to a result
   file (`internal/desktop/smoke.go:19-37,101-104,154-176`;
   `harness/lib/desktop-page.ts:32,273`).
   Every gate launch is **hidden** (`PASSQUEST_DESKTOP_HIDDEN=1`, `desktop-page.ts:283`) with timer
   throttling off precisely because "web views throttle the timers of a page that can't be seen to
   once a second (WebKit also suspends its CSS animations)" (`internal/desktop/desktop.go:162-170`);
   Windows and macOS hidden windows still lay out (`internal/desktop/hidden_other.go:7-9`), Linux
   forces the size (`hidden_linux.go:33`). So: **launch → `window.__pq.ready`** (`main.ts:116-127`)
   and the DOM-level interactions are measurable in the hidden windows the gates already use
   (wall clock from the harness, the page's `performance.timeOrigin + performance.now()` at ready);
   **rendering cost is not** — a hidden WebKit window suspends animations and does not composite, so
   frame timing needs a *shown* window, which no gate has ever used. What the engines offer:
   `performance.mark/measure`, `document.getAnimations()` and `requestAnimationFrame` exist in all
   three; `PerformanceObserver` entries `long-animation-frame`/`longtask` are Chromium-only (absent
   in WebKit) and are recorded as an optional WebView2 enrichment, never the primary metric; the
   app's own `Window.CapturePage()` ("a PNG screenshot of the visible page"; WebView2
   `CapturePreview`, WKWebView `takeSnapshot`) is available through MyGo
   (`mygo@v0.10.0/window.go:1811-1824`, `internal/windows/webview.go:1162-1189`,
   `internal/darwin/window.go:2132-2145`) and avoids OS-level capture, which on macOS needs the
   runner's screen-recording permission. **The tool** is `harness/tools/frontend-bench.ts`
   (the keychain tool's shape: a `bun`-run tool with `--self-check`, not a gate) with the pure
   verdict/shot functions in `harness/lib/bench.ts`: it takes `--a-root`/`--b-root`, launches each
   tree's own `build/desktop/passquest-desktop[.exe]` built by that tree's
   `bun run desktop:build` (`harness/desktop-build.ts`), **without** `PASSQUEST_DESKTOP_HIDDEN`,
   at `PASSQUEST_DESKTOP_CONTENT_SIZE=1280x800`, with a fresh data directory seeded once through
   the CLI and its own loopback provider stub; it alternates A and B serially in one job, **2
   warm-up launches per build, then 9 measured launches per build**, and records per metric the
   min/median/Q1/Q3/max plus **"worse beyond noise" = the head's Q1 above the base's Q3 *and* a
   median gap of at least the metric's floor (Amendment 13: `max(5 ms, 5 % of the base median, the
   larger control-pair side's IQR)` where the metric has control-pair samples in the run, `max(5 %,
   5 ms)` where it has none)**. Every measured launch requests a shown window
   (`hidden: false`) and records that request in its row; the record's shape check fails the run
   when a measured launch requested the hidden one, and that is what guarantees no number is
   measured in a hidden window — the guard cannot: WebView2 reports a hidden window as `visible`.
   Every timing launch is also guarded by the two StopRun-class checks —
   `document.visibilityState === "visible"` and the rAF tick budget (Amendment 1: 30 ticks within
   4000 ms) — which fail a window that actually stalls; the record carries each launch's
   `navigator.userAgent`, so ENOBUFS/cold-cache effects are visible. Metrics: `readyMs`,
   `answerSelectMs`, `submitFeedbackMs`, `coachReplyMs`, `roomSwitchMs` (report/anki/settings/
   assess), the rAF frame-duration sample during a scripted sheet-open + long-card scroll over the
   translucent layers (count, median, p95, longest), the optional LoAF totals, and the two bundle
   bytes. Screenshots are captured in a **separate launch per state** (timing is not polluted):
   the hook gains one test-only env `PASSQUEST_DESKTOP_SHOT_DIR` and a service `SmokeShot.Capture`
   (Go: `mygo.BindAs("SmokeShot", …)`; the page: `window.mygo.call("SmokeShot.Capture", name)`)
   that writes `<name>.png` via `Window.CapturePage()`; with
   animations settled (the ux gate's own `settle` trick) the same build must produce byte-identical
   PNGs — the **same-build control pair** the workflow can run with `a-ref == b-ref` is what proves
   the method and states the noise floor. **The workflow** is `.github/workflows/frontend-bench.yml`
   (the keychain workflow's shape): one `bench` job per OS — matrix `os: [windows-latest, macos-26]`
   — that resolves A and B (pull request base/head, or `workflow_dispatch` inputs `a-ref`/`b-ref`),
   checks both out, installs and builds both trees, runs the tool once, and uploads
   `frontend-bench-<os>` (JSON, log, shots; 30 days). Windows sets the 1920x1080 display the gate
   workflow sets (`.github/workflows/gate.yml:74-80`). Noise to expect: shared-runner CPU, cold
   WebView2/WebKit processes and profiles per launch, disk cache, and (locally) this machine's
   load; the control pair is the yardstick, and **no number is ever compared across machines or
   runs**.
5. **The invariance oracle today.** `desktop-ux` audits 24 states × 4 modes × 2 sizes — 192 audits,
   19 planted-defect probes, 84 focus checks, **0 allowed findings** (`harness/ux-allow.json` is

   `focus-lost`, `card-end-under-sheet`, `chosen-option-hidden`) and the MOTION probe
   (room transition must exist with motion allowed; no transition at all under reduced motion).
   `desktop-smoke` drives 13 scenarios and 488 assertions on Windows / 487 on macOS and Linux;
   `package-smoke` runs 9 cases over the installed package (counts from CI run `44639795066`,
   `docs/evidence/0015-know-when-a-newer-version-exists.md:29`; the 0019 runs re-quote them).
   **There is no pixel or screenshot comparison anywhere** — the 0012 discovery validated the
   library against 548 pixel samples by hand, and Q-0012-01 says screenshots alone are not evidence

## Defaults (append as Q-0019-01…06; the last entry is Q-0018-04)

1. **Q-0019-01 — The engine baseline.** WebView2: Evergreen current stable Chromium on Windows 11
   (157 at scout time; every sample records its UA). WKWebView: macOS 26's system WebKit, Safari
   26.x (runner: 26.6). WebKitGTK: 2.52.6 on `ubuntu-latest`, second-tier, must render and work.
   Feature level: JavaScript ES2024 (`tsconfig` `target`/`lib`), CSS as fact 1. The
   `frontend-baseline` gate pins the tsconfig values and scans for constructs outside the
   allowlist, so a target cannot drift from the docs.
2. **Q-0019-02 — The measurement method.** `harness/tools/frontend-bench.ts` +
   `.github/workflows/frontend-bench.yml`; visible windows; 2 warm-ups + 9 samples per build per
   metric; A and B serially in one job; median and IQR; "worse beyond noise" as fact 4 defines it;
   the same-build control pair is the noise floor; every number in the evidence record is quoted
   from a named run's artifact.
3. **Q-0019-03 — If a runner cannot show a window.** The rendering-cost metric then has no honest
   value: the run records the guard failure and the owner decides between accepting a disclosed
   proxy (style/layout cost measured hidden, compositing excluded) and a contract change. No
   proxy is invented silently.
4. **Q-0019-04 — The visual companion.** PNG captures through the smoke hook, base vs head from
   the same runner, same-build control first, `harness/frontend-visual-allow.json` for intended
   differences (stale entries fail). Companion to `desktop-ux`, never a substitute (Q-0012-01).
5. **Q-0019-05 — Features left out, with the reason.** Anchor positioning and `<dialog>`-free
   focus trapping for the popovers only if a Linux run proves the WebKitGTK behaviour; `@scope`,
   scroll-driven animations, view transitions and `content-visibility` stay out (no hand-built part
   they would replace, or a behaviour change the goal forbids). The evidence record lists each
   adopted feature with what it removed and each left-out candidate with its reason.
6. **Q-0019-06 — What stays.** `-webkit-font-smoothing` and the `::-webkit-scrollbar*` family stay,
   because they are WebKit's own APIs with no equivalent that keeps the design's text weight and
   8 px thumb; they are allowlist entries with that reason, and the gate fails on an entry that
   matches nothing. No new dependency is added: the shot comparison is byte equality, not an image
   library.

## Risks (each with how it is detected)

- **A runner cannot show a window** (macOS most likely) → the launch fails outright or the rAF
  budget fails the sample by name; WebView2 cannot be canvassed this way (a hidden window there
  reports `visible` and keeps ticking), so the guarantee that no number is measured in a hidden
  window is structural: every measured launch records the visibility it requested (`hidden:
  false`) and the record-shape check fails the run when one requested the hidden window. P1's
  control run is where it is learned; the owner decides per Q-0019-03.
- **P1's hook changes the app** → the binding is registered only with the shot env; the desktop
  smoke's new assertion (an unbound `SmokeShot.Capture` call rejects by name) and the package
  smoke's `study` case run without it.
- **The bench noise swamps the metrics** → the same-build control pair's own "worse" verdict; if it
  fires, the run's comparisons are not read and the tool's sample count/warm-up or metric list is
  redesigned; never a cross-run comparison.
- **The capture is nondeterministic** (animations, scroll position, window occlusion, a black
  screen) → the same-build control pair's shots differ; the run records which states and the shot
  rows are unusable until the cause is fixed.
- **Removing `-webkit-backdrop-filter` changes rendering** (WebKit's unprefixed implementation is a
  rewrite) → a shot difference or a `contrast-*` finding on macOS or Linux; the step either allows
  it with a stated reason or reverts the removal for that engine.
- **`<dialog>` breaks the modal audits** → `modal-not-trapping`, `dialog-focus-*`,
  `primary-*`, `contrast-*` findings; the step teaches the library only with a must-fail self-test
  case, or reverts and discloses.
- **A popover changes hit-testing** → `layout.interactive-covered/-not-hit`, `primary-hidden`,
  `focus-lost` findings; revert that overlay, disclose.
- **Container queries move a layout at the 1340 boundary** → layout/primary/unreachable findings at
  one of the two audited sizes; revert that rule.
- **Nesting/`@layer` reorder the cascade** → any ux finding at all; one stylesheet family per
  commit keeps the culprit named.
- **The A build fails in the workflow** (a base predating an import the tool needs) → the workflow
  log; the tool only ever uses its own tree's harness and A's binary, and it refuses a missing
  binary by name.
- **This Windows machine is at 100 % CPU** (the brief's known fact) → local bench runs are advisory;
  CI is the authority, and the control pair says whether a local run is readable at all.
- **The goal's 135 is quoted by someone as fact** → fact 2's commands and counts are in the
  evidence record; the number is marked not reproduced instead of re-invented.
