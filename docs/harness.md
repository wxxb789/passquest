# Harness

The harness is the part of this repository that makes a claim checkable by a machine. It is expected
to grow with the product: a new capability that nothing can verify is unfinished work.

Binding project conventions (stack, truth ownership, layout, uncertainty protocol):
[`conventions.md`](conventions.md).

## One entry point

```bash
bun run gate
```

`bash scripts/gate.sh` remains a compatibility shim that execs the same command. There is no second
gate definition: CI and a local run both call `harness/gate.ts` through the root `gate` script.

The harness is a **Bun + TypeScript program** — one module per gate under `harness/gates/`, shared
code under `harness/lib/`. File-based gates read the working tree: tracked paths plus untracked,
non-ignored paths that exist, so a pre-commit run scans new deliverables and does not fail on a
pending archive move. The list is walked once per gate run, on the first file-based gate, and shared
by every later file-based gate; a listed file removed since then is skipped, not reported unreadable.
Gates that drive the CLI share one build of `./cmd/passquest` per gate process and per root
(`buildCLI` in `harness/lib/go.ts`), so a self-test fixture root still gets its own build.
Decision and rationale:
[`decisions/D-0001-bun-typescript-harness.md`](decisions/D-0001-bun-typescript-harness.md). The
migration landed with goal 0002; no `bash` or `python3` gate scripts remain.

CI (`.github/workflows/gate.yml`) runs `bun install --frozen-lockfile` and then
`bun run gate --group <group>` as one job per OS (ubuntu, macos, windows) and gate group: `core`
(gates 1-23), `desktop` (24-25), `package` (26) and `self-test` (27), with fail-fast off, so a failure
costs one group's wall time and a re-run repeats only the failed job. With no argument, `bun run gate`
runs all 27 gates in order. Every `bun run gate`, with or without `--group`, refuses to run unless the workflow
matrix is exactly `os` (ubuntu-latest, macos-latest, windows-latest) × `group`, with no
`include`/`exclude`, lists exactly the groups declared in `harness/gates/index.ts`, passes each cell's
group through `GATE_GROUP` to `bun run gate --group "$GATE_GROUP"`, and every gate is in exactly one
group (`harness/lib/gate-groups.ts`); an unknown group fails. On ubuntu the `desktop`, `package` and
`self-test` jobs install WebKitGTK 4.1, xvfb, gnome-keyring and (for the AppImage) desktop-file-utils,
and run inside `dbus-run-session` with a keyring unlocked by a throwaway password, so the desktop
smoke has a webview, a display and a Secret Service; on Windows those jobs set a 1920x1080 display.
macOS uses the login keychain and Windows the
Credential Manager. Every PASS/FAIL/SKIP line ends with the gate's wall time (`[3.2s]`) and the run
ends with a slowest-first timing table. A failed job uploads its full gate output as the
`gate-output-<os>-<group>` artifact, and the `package` job uploads the package this run built as the
`package-<os>` artifact (7 days; an inspection artifact). A pushed `v*` tag runs this whole workflow
through `release.yml`, whose release job drafts a GitHub Release from those artifacts ([`release.md`](release.md)). The four jobs of one OS
share setup-go's cache key, so only the first to finish saves the build cache (Q-0012-08). A green
Linux job is not evidence for Windows; the matrix is the evidence.

## What CI proves and what it does not

- CI runs `bun run gate --group <group>` for each of the four groups on Linux, macOS and Windows;
  together the groups are the full gate. Platform-specific packaging, WebView or Anki
  behaviour still needs its own runtime evidence; the matrix is not a desktop-app test.
- The frontend bench is a tool and a workflow, not a gate (Q-0019-02): `harness/tools/frontend-bench.ts`
  measures a base commit A and a head B on the same runner, one job per OS `windows-latest` and
  `macos-26`, alternating 2 warm-ups + 9 launches per build per metric in visible windows at a
  1280x800 page area (Q-0012-05), records each launch's engine user agent and the visibility guard,
  and decides "worse beyond noise" per metric against a floor the record names: `max(5 ms, 5 % of the
  base median, the metric's larger control-pair IQR)` where the run measured a control pair, `max(5 %,
  5 ms)` where it did not (Q-0019-02); the goal-0019 evidence record quotes every number from a named
  run's `frontend-bench-<os>` artifact, and a same-build run (A = B) validates the method (its shots
  byte-identical, its A/B verdict judged by the fixed `max(5 %, 5 ms)` floor).
  A run whose same-build pair reads worse discards that attempt and measures again inside the same
  job — fresh A, B and control launches for every metric, at most two re-measures (three attempts, the
  same rules on every OS, and the workflow's 60-minute timeout holds them) — and the verdict is the
  first attempt whose pair reads ok: a readable attempt's `WORSE` verdict stays final and is never
  re-measured away, the shot captures stay once-per-run and are not per-attempt, and every attempt's
  numbers, with why a discarded one was discarded, stay in the log and the record's `attempts` block
  (Q-0019-02, owner decision 2026-11-26).
  The shot states are seven — `today` and `today-dark` (both appearances of the today view, 0022's
  Done-when 1), then `sheet-open`, `practice-independent`, `feedback-coach`, `settings-row` and
  `report`; every shot launch's row carries the room `--mygo-titlebar-*` reported and the page's
  `:root[data-titlebar]` marker, and each compared state's row carries the OS scope the shots were
  read under, which with the run's head branch decides which `harness/frontend-visual-allow.json`
  entries apply (an entry's optional `os` is `windows`, `macos` or `any`, and its optional `branch`
  is the pull request's own head branch, which the workflow passes — a dispatch passes none; an
  entry scoped to another OS or branch, or to any branch in a run that has none, neither allows a
  difference nor reads as stale, Q-0022-06).
  `--smoke` renders the seven shot states in a visible WebKitGTK window on the Linux job, second-tier
  and comparing nothing: its record carries each state's `readyMs` but compares nothing; the tool's
  `--self-check` runs before the builds, so a broken parser fails in seconds
  (`.github/workflows/frontend-bench.yml`).
- The Homebrew cask is proved by a workflow, not a gate: it downloads a published release, clones
  the public tap and runs `brew`, so it needs a macOS runner, the network and a release that
  exists (`.github/workflows/cask.yml`, goal 0017). A gate makes no external network call. What a
  gate can hold still, `install-guide` does: it pins the template's v0.15.0 render byte for byte on
  all three OSes, while the workflow installs that render from the tap and asserts the quarantine
  flag is gone, the installed app boots, `brew uninstall --zap` quits it and removes the bundle and
  every path the cask's `zap trash:` names (the data directory and the app's WebKit data and cache
  folders under `~/Library`, read from the installed cask file rather than a list in the tool), and
  three mutant runs catch the removal each behavioural assertion depends on: without
  `postflight_steps` the quarantine flag is still there, without `zap trash:` the data directory
  survives, without `quit:` the app keeps running.
- The macOS Keychain upgrade experiment is a tool and a workflow, not a gate: no gate can click the
  Keychain prompt it exists to record, and the run is four `macos-26` jobs of two package builds each
  (`arm: [adhoc, self-signed]` × `keychain: [experiment, login]`; `.github/workflows/keychain.yml`,
  `harness/tools/keychain-experiment.ts`, goal 0018). It builds two packages from two commits, installs
  one over the other and records what the second build's read meets; goal 0018 is parked until a
  Developer ID exists (Q-0018-02…04), so its `pull_request` trigger covers only the workflow and the
  tool's repo-local import closure. The `project` arm is the revisit path and is **not** in the matrix
  today (`arm: [adhoc, self-signed]`, and no step passes the two signing secrets): with a Developer
  ID, store it as the two secrets, add `project` to the workflow's `arm` matrix, then run the
  workflow by `workflow_dispatch` (Q-0018-04).
- `.github/workflows/gate.yml` checks out with `fetch-depth: 2`. That keeps the clone shallow while leaving
  the change's base reachable as `HEAD^1`, which is what the golden-contract gate diffs against in CI; a
  depth-1 checkout cannot see a golden change at all and the gate refuses instead of passing. On a
  multi-commit push to the default branch a depth-2 checkout shows only the tip commit — the pull request
  run is what checked the whole branch.
- CI is a floor. A merged pull request additionally needs the machine review marker and a local gate
  re-run on the exact head being merged.
- Do not run the full gate chain twice on one commit and call it two proofs. The local run on the
  final tree is the evidence; CI confirms it reproduces from a clean checkout.
- Do not run the import smoke or a benchmark concurrently with the full Go test suite on a
  memory-constrained host; they are cheap, but the Go toolchain parallelises packages by default.

## Growth policy

Add a gate when, and only when, a real failure mode exists that the current set cannot see:

| New surface | Gate it should bring |
|---|---|
| JSON/CLI protocol or persisted schema | golden-file or schema test, and a migration test from the previous version |
| Local practice CLI | first-party import scan for network packages and confidential markers (`local-only.ts`) |
| Import / OCR | fixture-based test with a deliberately damaged input, plus an explicit "unverified" state assertion (`import-smoke.ts` and Go tests) |
| Scoring tactic / assisted evidence | guided/independent smoke with key hiding, stage gating and an assisted-vs-independent report split (`tactic-smoke.ts`) |
| Adaptive selection / skill evidence | recommendation smoke separating recorded evidence from inference, with passage re-exposure, hints, revisits and reopen stability (`adaptive-smoke.ts`) |
| Private source baseline | provenance/manifest integrity and test/fixture isolation (`baseline.ts`) |
| Provider call | recorded-fixture test with the network disabled; a failure path that cannot corrupt attempts (`tutor-smoke.ts`, plus Go prompt/consent/store tests) |
| Durable agent / Pi runtime | real host restart, pause/resume, cancellation and reconciliation of a retried effect (`agent-smoke.ts`, plus Go packet/store/CLI tests) |
| Anki integration | fake AnkiConnect server test (idempotency, conflict, offline queue, read-back of the deck a card reached) — never a real deck |
| Desktop shell | a hidden-window launch that fails on a blank window and drives real flows through the page; screenshots alone are not evidence (`desktop-smoke.ts`) |
| Visual and interaction quality | in-window measurement per route × theme × language × size against an allowlist that only shrinks, with planted-defect probes on every run (`desktop-ux.ts`) |
| Installable package | the platform's own package installed into a temp prefix and the installed app driven with no developer tool on `PATH`, whose per-user data must outlive a relaunch and a reinstall (`package-smoke.ts`) |

Rules for the harness itself:

- A check that always passes is worse than no check: it converts an unknown into a false green.
  Delete it, or give it an input that must fail: a case in `harness/gates/self-test/<gate module>.cases.ts`
  listed in `brokenCases()` in `harness/gates/self-test.ts`.
- A check that depends on a network call belongs in CI only if the call is deterministic; otherwise
  record the fixture.
- Keep gate output short and numeric: counts, exit codes, paths.
- New checks are TypeScript gate modules sharing `harness/lib/`; never another `scripts/*.sh` or
  `scripts/*.py` one-off. Duplicate logic between gates is a harness defect.

## Environment

- Toolchain is pinned by `mise.toml` (Go, Node, Bun). A contributor without mise needs matching Go,
  Node and Bun on `PATH`; `python3` and a POSIX shell are not required. Node runs the product's
  four agent hosts (tutor, search, Anki, Pi Durable) and the smokes that drive them; the rest of the
  CLI and all local practice tests stay Go-only. Packages bundle their own pinned Node.
- `tutor-smoke`, `find-smoke` and `agent-smoke` start loopback stubs in the gate process. They make no
  external network call and use a generated credential that exists only in the gate's memory.
- `agent-smoke` also runs the real Node + Pi Durable runtime against a temporary Pi SQLite file. It
  needs the workspace dependencies installed; a missing `node_modules` fails the gate rather than
  silently skipping the runtime.
- `bun install` installs the two harness dev dependencies (TypeScript and Bun types) used by the
  typecheck gate plus the pinned Pi Durable workspace under `agent/`; `bun.lock` is committed so the
  install is reproducible. CI runs the same install before the gate.
- The Windows package smoke refuses to install (after its build, before the installer runs) while
  `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\com.github.wxxb789.passquest` registers an
  install outside its temp tree, or while `Pass Quest.lnk` (the name MyGo's `shortcutName()` builds)
  exists in the `Programs` or `Desktop` shell folder — a real Pass Quest install on the machine must
  be uninstalled first: the installer writes that key and those shortcuts and, without `/D=`, the
  default install directory a learner's copy uses. Its own install is removed on every exit path the
  gate controls; a run killed from outside (Ctrl-C, a job timeout) can leave it registered, and the
  next run then refuses until that copy is uninstalled.
- Private material lives under `data/private/`, `data/local/`, `local-data/`, or `.passquest/`
  (gitignored). Nothing there may be copied into `testdata/`.
